# Repository Automation Guide

This file contains repository-specific instructions for automated coding agents and review harnesses. User-facing documentation belongs in `README.md`; contributor instructions belong in `CONTRIBUTING.md`; maintainer release-signing details belong in `docs/RELEASE_SIGNING.md`.

## Project identity

The following values form one atomic identity and must remain consistent:

- Display name: `Pixelify Infinity`
- Application ID / namespace / Kotlin package: `io.github.samson910022.pixelifyphotos`
- Xposed entry point: `io.github.samson910022.pixelifyphotos.PixelifyModule`
- Xposed scope: `com.google.android.apps.photos`

Do not restore the legacy active package `balti.xposed.pixelifygooglephotos`. Historical attribution may mention it in migration documentation.

## Safety invariants

- Never read, print, copy into the repository, stage, or commit private signing material.
- Forbidden repository content includes private keystores, private-key PEM files, passwords, recovery shares, local signing properties, and private backup topology.
- Only the public certificate and its SHA-256 fingerprint belong in Git.
- Never change GitHub repository visibility, publish a release, submit to an external repository, rotate the application ID, or rotate the release key unless the user explicitly requests that exact action.
- Do not commit generated APK/AAB files or `app/build/` output.
- Do not expose account identifiers or private data from logs and test fixtures.

## Required workflow

For multi-phase maintenance work:

1. Inspect the current working tree and preserve unrelated user changes.
2. Make one coherent phase of changes.
3. Run phase-appropriate checks.
4. Assign an independent reviewer that did not implement the phase.
5. Resolve blocking findings before starting the next phase.
6. Before commit, run the full release gate and inspect the exact staged tree.

Review reports generated by an automation harness are ephemeral working artifacts and should not be committed unless the user explicitly asks for an audit archive.

## Verification commands

Use JDK 17 and an Android SDK containing Platform 36. The standard full gate is:

```bash
./gradlew --no-daemon --no-configuration-cache \
  test lintDebug lintRelease assembleDebug assembleRelease bundleRelease
```

For a maintainer-authorized signed build, supply signing configuration from outside the repository and run the fail-closed release task:

```bash
./gradlew --no-daemon --no-configuration-cache \
  :app:verifiedRelease
```

Then run `./scripts/check-publication-readiness.py --require-artifacts` and verify the final APK/AAB signers independently.

Never echo signing environment variables. Verify final artifacts with `apksigner`/`jarsigner` without printing secrets.

## Public-document rules

- `README.md` is English-first and written for installers and users.
- Keep language links synchronized across translated READMEs.
- Do not place build internals, test counts, review-harness history, private backup design, or signing-property examples in the public landing page.
- Put developer build instructions in `CONTRIBUTING.md`.
- Put only non-secret signing policy and public verification information in `docs/RELEASE_SIGNING.md`.
- English documentation is authoritative; translations must link back to it and identify themselves as translations.

## AI review bot

Maintainer-facing documentation for the advisory GitHub issue/PR bot lives in [docs/AI_REVIEW_BOT.md](docs/AI_REVIEW_BOT.md). Package overview: [github_bot/README.md](github_bot/README.md).

When changing bot behavior:

1. Keep issue investigation and PR code review on separate report formats and sticky markers.
2. Do not print model names, provider names, or routing details in public comments.
3. Prefer fail-closed structured stubs over truncated free-model prose for issue investigation.
4. Run `PYTHONPATH=github_bot/src python3 -m unittest tests.test_ai_review_bot -v` for bot changes.
5. User-facing contributor notes belong in [CONTRIBUTING.md](CONTRIBUTING.md) and [SUPPORT.md](SUPPORT.md); do not put bot internals on the public README landing page.

## Pre-commit checks

- `git diff --check`
- no active references to the legacy package outside migration/history documentation
- no private-key containers, private PEM headers, credentials, or local paths
- application ID, namespace, module entry, scope, versions, and update metadata agree
- public certificate fingerprint matches documentation and signed APK
- unit tests and lint complete without errors
- GitHub remote remains private unless the user explicitly requests publication
- before any future public launch, complete `docs/PUBLICATION_CHECKLIST.md` under a separate authorization
